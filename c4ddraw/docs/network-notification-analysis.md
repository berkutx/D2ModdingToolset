# Сетевое уведомление: причина остановки и границы исправления

Дата анализа: 2026-09-21. Здесь описаны проверенный дефект протокола и предлагаемое исправление во врапере. Анализ не устанавливает причину каждого чужого зависшего матча. Реализация проверена изолированными тестами и сборкой; живого сетевого прогона новой DLL пока не было.

## 1. Как очередь останавливается при работающем UI

Источники: [CNetCustomPeer](../../mss32/src/netcustompeer.cpp), методы `UpdateThreadCallback` (строки 59–79), `SendPacketNotification` (82–97), `ResetPacketNotification` (54–57); [CNetCustomService](../../mss32/src/netcustomservice.cpp), `peerProcessEventCallback` (622–657). Флаг [m_packetNotificationSent](../../mss32/include/netcustompeer.h) — atomic: ошибка логическая, а не неатомарный доступ к памяти.

Worker проверяет нижнюю очередь и отправляет уведомление, только если она не пуста и `sent=false`. Важен порядок присваивания:

```cpp
m_packetNotificationSent = uiManagerApi.postMessage(...);
```

Запись флага происходит после публикации сообщения. UI может выполнить callback раньше этой записи.

| Шаг | Worker | UI |
|---|---|---|
| 1 | Публикует сообщение о пакете A, приостанавливается до записи результата | |
| 2 | | Получает сообщение, обрабатывает A, сбрасывает `sent=false` |
| 3 | Возобновляется и записывает `sent=true` | Callback уже завершён |
| 4 | Приходит B; `sent=true` запрещает следующий post | Windows-уведомления больше нет |
| 5 | Продолжает проверки с тем же результатом | Меню/мышь/прочие события продолжают работать |

Такое исполнение допускается и при успешном PostMessage. Оно не требует сбоя сервера или бесконечного лишения worker процессорного времени. Поздняя запись флага конечна, а полученное состояние устойчиво.

В изолированном исследовательском стенде неизменённые методы MSS, настоящие producer/UI потоки и Win32 очередь воспроизводили этот порядок: 1 024 последующих проверки worker и 32 посторонних UI-сообщения не продвигали нижнюю очередь. Штатное дополнительное уведомление доставляло накопленное FIFO без повторов. Барьер задавал допустимое расписание; естественная частота гонки этим тестом не измерялась.

## 2. Почему одного повтора недостаточно

**Контрпример для любого конечного N.** После первого успешного post задержим worker перед поздней записью `true`. UI обслужит исходное уведомление и все N дополнительных повторов. Затем worker продолжит старую запись; следующий пакет опять останется без уведомления. Любой конечный набор повторов можно расположить до этой записи. Поэтому ни один повтор, ни N повторов, ни увеличение интервала сами по себе не дают гарантии.

**Достаточность независимых возобновляемых попыток.** Возьмём поступивший пакет P, перед которым находится конечное число пакетов. Пусть регистрация живёт, внешний UI-цикл получает выполнение, повторные post в итоге успешны, вложенные окна в итоге возвращают управление, а `Receive` и packet callbacks завершаются. Тогда независимое уведомление в итоге вызовет штатный receiver. Он дойдёт до P либо P будет обслужен ещё раньше настоящим уведомлением. Значение `sent` не запрещает независимый сигнал. Предположение, что P бесконечно не обслуживается только из-за потерянного уведомления, противоречит этим условиям.

Это гарантия последующего продвижения, не жёсткий timeout в миллисекундах. Она не чинит отсутствие пакета от сервера, бесконечный callback, вечный `processing=true` или остановившийся внешний UI-loop. При бесконечном отказе PostMessage гарантии тоже нет.

Конечная модель подтверждала контрпримеры для N=0/1/2/3/5/10 и отсутствие устойчивой недоставки при возобновляемом сигнале и явных условиях прогресса. Это проверка редуцированной модели; приведённый аргумент не зависит от выбранных этих шести значений N.

## 3. Требования к wrapper-only восстановлению

- Отслеживать настоящую регистрацию/удаление `MIDGARD CUSTOM LOBBY NETMSG` через проверенный EXE; не зашивать адрес callback или private layout пересобираемого MSS.
- Не активировать защиту только по имени сообщения: MSS регистрирует listener до создания peer. Начинать после завершённого настоящего matching callback при живом поколении регистрации, наблюдая завершение в том числе во вложенном окне.
- Держать не более одного собственного ожидающего запроса; резервировать его до post, чтобы не повторить исходную late-store гонку. Проверять поколение при отправке, обслуживании и отмене.
- Доставлять повтор через штатную внешнюю диспетчеризацию; внутри modal/вложенного callback только откладывать. Не вызывать Receive из рендера/таймера и не создавать вложенный pump.
- Отменять запросы при удалении listener/окна/контроллера. Не повторять `MQ_COMMANDQUEUE2`: это уже игровая очередь команд с другим контрактом.
- Возобновлять попытки независимо от MSS-флага и низкоприоритетного игрового WM_TIMER. Fail-closed при неизвестном EXE или неполном наблюдении жизненного цикла.

Эти требования задают границы предлагаемой реализации, а не утверждают, что произвольная интеграция hooks автоматически им соответствует.

## 4. Отдельный конфликт таймеров C4

До правки C4 устанавливал `SetTimer(gameHwnd, 0xC4D7, 32, nullptr)` и поглощал WM_TIMER с ID 50391: [исходная featuremenu.cpp](https://github.com/berkutx/D2ModdingToolset/blob/4757790b27f029f5e2f5f5ae33937a8f79fed055/c4ddraw/features/featuremenu.cpp). Исследованный EXE начинает timer ID с 1 (`00562755`) и увеличивает после успешного SetTimer (`00562CF8`), без исключения для C4.

Когда счётчик достигает 50391, native SetTimer заменяет слот врапера на общем HWND; C4 поглощает уже игровое событие. Последующий KillTimer удаляет тот же слот. Нужны 50391 накопленное успешное создание, а не столько одновременно активных таймеров. Время достижения неизвестно; этот механизм сам по себе не объясняет пропажу registered-message уведомления об отключении хоста.

Собственный HWND отделяет пространство таймеров врапера от игрового. Больший магический ID лишь откладывает конфликт. Разделение HWND проверялось на настоящих Win32 таймерах; безопасность вызова игровых maintenance callbacks во вложенных окнах остаётся отдельным требованием.

Native сведения получены через IDA Pro MCP для EXE SHA-256 `1375CDEF09EC470EE64FE5693FB734D7C69FB215212311D997F792B258A642EB`; соответствие исследованных диапазонов проверено байтами. Это анализ конкретного EXE, не обещание работы на любом бинарнике игры.

## 5. Реализация и проверка предлагаемой правки

[netnotify.cpp](../features/netnotify.cpp) наблюдает native регистрацию, удаление и завершение callback. После настоящего сетевого callback отдельный worker раз в секунду пытается поставить один частный запрос. [WakeState](../features/netnotifystate.h) резервирует token до PostMessage и отсеивает старые поколения. Накопления повторов нет. Во вложенном loop запрос откладывается; общий внешний путь возвращает его в обычную очередь с новым token. [messagebatch.cpp](../features/messagebatch.cpp) преобразует только выбранное сообщение на штатной внешней границе DispatchMessage. Это работает и при `messageBatching=0`. Владелец меню явно передаёт функцию проверки recovery-настройки и обработчик выбранного сообщения при установке общего hook; настройка читается однократно, batching не связан напрямую с модулем восстановления.

Worker не читает внутреннюю очередь MSS и не вызывает игру. Адреса MSS не используются; совместимость опирается на проверенный native EXE и контракт существующего сообщения. При неизвестном EXE, неоднозначной регистрации или недоступном наблюдении защита остаётся выключенной. Интервал 1 с — период попытки, не обещанный срок восстановления. По успешной доставке уведомления нельзя заключить, что был восстановлен пакет: счётчики трассировки этого не утверждают.

Настройка `[menu] networkWakeRecovery=1` включена по умолчанию; `0` отключает её после перезапуска. [OwnedWindowTimer](../features/ownedwindowtimer.h) переносит прежнее обслуживание C4 на отдельный message-only HWND того же UI-потока; ID 50391 на игровом HWND больше не перехватывается. Сетевой worker от этого таймера не зависит. MSS и игровые команды не меняются.
