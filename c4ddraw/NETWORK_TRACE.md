# Диагностика передачи хода

`C4trace` по умолчанию пишет короткий сетевой журнал: отправку и получение BeginTurn / EndTurn / TurnInfo, обработку TurnInfo, отключение и сводку раз в пять секунд. Остальные пакеты только считаются; их содержимое не сохраняется. Это **диагностика, не исправление и не средство разблокировки игры**.

По умолчанию выключен. Инструкция относится к C4dll-R с `eventtrace` и `inventorytrace`. Для трассы не нужно подменять `mss32.dll`.

> Трассировка сама меняет timing: добавляет короткие замеры, атомарные операции, попытку захвата lock и отдельный поток записи. Отсутствие бага с включённой трассировкой не доказывает его устранение. Не меняйте одновременно `singlecpu`, `maxgameticks`, FPS, VSync, FastAI и скорости анимации: иначе причины будут смешаны.

## Включить и проверить

**Сначала сохраните игру.** В меню выберите «Производительность > Технические настройки > Диагностика сети и задержек (рестарт)...» (`Performance > Technical settings > Network/timing diagnostics (restart)...`). Подтверждение переключения сохраняет `netTrace` и **сразу закрывает текущий клиент**. Запустите игру заново вручную: только новый запуск прочитает настройку. Автосохранения и автоматического повторного запуска нет; несохранённый прогресс может пропасть, а сетевое подключение будет разорвано.

Если редкое зависание уже поймано, **не переключайте этот пункт и не используйте общий сброс**: они закроют ценный для исследования процесс. Сначала сохраните имеющиеся CSV и согласуйте дальнейшую диагностику.

При `C4DLL_NETTRACE=1` меню сообщает, что диагностика принудительно запрошена переменной окружения, и не позволяет выключить её. Уберите эту переменную из окружения будущего запуска либо задайте `0`; после этого можно использовать обычный переключатель. Общий сброс настроек враппера не отменяет внешнюю переменную.

Альтернатива меню: в согласованном тестовом инстансе, **до его запуска**, добавьте в существующую секцию `[menu]` файла `C4menu.ini`:

```ini
[menu]
netTrace=1
```

Не заменяйте этим фрагментом весь файл и не создавайте вторую секцию `[menu]`, если она уже есть. Альтернатива — переменная окружения `C4DLL_NETTRACE=1`, унаследованная только запускаемым тестовым процессом. Системную переменную для всех программ создавать не требуется.

Включение — логическое **ИЛИ**: `netTrace=1` либо `C4DLL_NETTRACE=1`. Для выключения нужны одновременно `netTrace=0` и отсутствие внешней `1`. `true`, `yes`, `01`, `1junk` не включают трассу. Настройки читаются один раз при первом GUI-dispatch, не из `DllMain`. Ручная правка INI не переключает живой recorder; меню после сохранения закрывает клиент именно для нового старта, а не переустанавливает наблюдатели на лету. Если два клиента используют одну папку, INI общий, но закрывается лишь выбранный процесс; второй прочитает новую настройку только при своём следующем запуске.

После старта рядом с `Discipl2.exe` должен появиться новый файл:

```text
C4trace-<PID>-<UTC-start>-<QPC-start>-<attempt>.csv
```

Это шаблон имени, не команда. Каждый процесс создаёт свой файл через `CREATE_NEW`, старые логи не перезаписываются. Если лог не появился, проверьте: нужную диагностическую DLL, точную настройку, наследование переменной окружения, права записи в каталог и минимум 64 МиБ свободного места на его диске. Длинный путь, ошибка диска или инициализации могут оставить диагностику выключенной; игра при этом продолжает обычный путь.

Отметка настройки или принудительное включение через окружение не гарантируют, что writer ещё работает: проверяйте рост нужного CSV и его `#stop`.

## Что собрать при зависании

Включите диагностику до матча у хоста и джойнера. После зависания сохраните оба `C4trace-*.csv` и укажите, кто вручную завершил ход. Если клиент ещё работает, подождите несколько секунд для фоновой записи. Дамп для этой первой проверки не нужен.

Строка `#mode,network-minimal` подтверждает короткий режим. Проверяйте доступность наблюдателей: `200` содержит маску установленных сетевых точек, `201` — причину пропуска; `222` — TurnInfo, `225` — отключение. При несовпадении игрового EXE или изменённой точке наблюдатель пропускается. Адреса и внутренние поля MSS не используются; сохраняется реальная виртуальная функция, переданная игре. Это покрытие стандартных вызовов поддержанного EXE, а не обещание перехватить любые дополнительные вызовы стороннего мода.

Отправка с успешным результатом означает принятие локальным сетевым кодом. Если соответствующего получения нет, остаются отправляющий MSS, транспорт/лобби и принимающий MSS. Получение с последующим незавершённым TurnInfo сужает поиск до принимающего клиента. Завершение обработчика ещё не доказывает правильное игровое состояние.

Сопоставляйте класс, длину, полный 64-битный отпечаток, направление и порядок. Одинаковые повторные сообщения имеют одинаковый отпечаток; это не уникальный номер. Часы разных компьютеров не считаются синхронизированными. Потери записей, недоступный observer и незаписанный хвост журнала не означают потерю пакетов.

Сводка UI доказывает только прохождение оконных сообщений через врапер; она не доказывает продвижение сетевой очереди. `lastCount` — последний результат уже выполненного игрой вызова, а не текущий опрос очереди. Счётчики накопительные, 32-битные, каждый читается атомарно, но вся сводка не является одной атомарной фотографией.

### Поля короткого журнала

`role`: 0 — клиент игры, 1 — игровой сервер хоста. На хосте могут встречаться обе роли. `ordinal` — локальный номер наблюдения, не сетевой sequence. Маска точек: 1/2 — client/server send, 4/8 — receive, 16/32 — реальные count-вызовы; полная маска — 63.

|---:|---|---|---|---|---|

| 201 | адрес точки или 0 | причина: 1 EXE, 2 изменённый код, 3 detour, 4 архитектура | маска | ошибка detour | 0 |
| 202 | netPlayer | ordinal | role | получатель | фактический send target |
| 203 | netPlayer | ordinal | role | результат send | LastError после send |
| 204 | netPlayer | ordinal | role | отправитель | фактический receive target |
| 205, описание | netPlayer | ordinal | kind \| (status << 8) | длина | чтение sender: 0 неприменимо, 1 успешно, 2 не удалось |
| 205, отпечаток | netPlayer | ordinal | 0x80000000 | младшие 32 бита | старшие 32 бита |

| 210 | role | sends | sendFailures | receives | receiveSuccess |

| 243 | controller | custom message ID | поколение | 0 | 0 |

`240` означает установленную защиту; `243` — её активацию после первого завершённого
настоящего уведомления этой регистрации. `244` записывается примерно раз в пять
секунд отдельным worker при живой регистрации. Счётчики относятся только к
механизму врапера: успешный синтетический dispatch не доказывает наличие пакетов,
остановку очереди или восстановление конкретного матча. Защита работает независимо
от включения трассы; `networkWakeRecovery=0` отключает её после перезапуска.

`kind`: 1 BeginTurn, 2 EndTurn, 3 TurnInfo. `status`: 0 пусто, 1 неполный заголовок, 2 неверный заголовок, 3 другой класс, 4 неполная выбранная запись, 5 выбранная запись больше 1024 байт, 6 полностью прочитана. Отпечаток достоверен только при status=6; его отсутствие/нулевое значение при другом статусе не подходит для сопоставления.

Состояние disconnect: 1 установлен, 0 не проверен, -1 неподдержанный EXE, -2 изменённый entry/vtable, -3 ошибка detour. Отрицательные значения в x86 CSV представлены беззнаковыми hex. Вызов disconnect может оставаться открытым, пока игрок не закроет показанный игрой диалог.

Сетевые счётчики и UI записываются раз в пять секунд при работающем GUI. Empty/failure receive не читают выходной буфер. `receiveFailures` включает любой результат кроме 0 и 2; `malformed` считает нечитабельные/неполные заголовки и неполную выбранную запись, а не все ошибки игры. Ни один из этих признаков сам по себе не устанавливает причину зависания.

В релизном архиве есть необязательный анализатор `Tools/analyze-event-trace.py` (Python 3). Для самой записи журналов Python не нужен. Из папки распакованного архива:

```powershell
python Tools/analyze-event-trace.py "C:\path\C4trace-....csv"
```

Анализатор показывает доступность точек, последние выбранные сообщения с отпечатками и результатами send, длительности TurnInfo/disconnect и сводные счётчики. `--json` выводит все наблюдения. Он не сопоставляет автоматически часы разных компьютеров и не назначает виновника.

## Подробная трасса задержек

Ниже описан сохранённый подробный режим. Для него дополнительно задайте `C4DLL_NETTRACE_DETAIL=1` в окружении конкретного запуска. Одной этой переменной недостаточно: диагностика также должна быть включена обычным способом. Режим считывается при старте; значения `true` и `1junk` не принимаются. В CSV будет `#mode,detailed`.

В коротком режиме старые события кадров, мыши, часов, очереди инвентаря и каждого PostMessage не пишутся. Их дополнительные наблюдатели не устанавливаются. Лимит файла остаётся 32 МиБ; при достижении запись остановится с причиной `cap`, поэтому это необходимо учитывать при разборе.

## Совместимость: два уровня наблюдения

- **Общий Win32-уровень:** доступные пути оконных сообщений, ожиданий и вывода враппера не фиксируют версию мода или хэш игрового EXE. Post/Register наблюдаются через именованные импорты USER32 самого EXE, не всех DLL процесса. Конкретное событие появится лишь там, где соответствующий путь/импорт доступен; это не обещание полного покрытия любого EXE и рендерера.
- **Игровые очереди и manager:** подробные send/ingress/apply/notify и чтение manager допускаются только после проверки неизменного `Discipl2.exe`. Очереди дополнительно проверяют точные сигнатуры каждой точки перехвата. Другой EXE или изменённый модом пролог означает пропуск наблюдателя (`UNAVAILABLE`, причина ниже), а не переход по чужому JMP и не попытку перехватить код внутри мода.
- **События боя и FastAI:** приходят из уже существующих timer/battle/FastAI hooks, у которых свои проверки версии/размера EXE и нативных прологов. Нельзя приписывать событиям 60–71 тот же полный SHA256-gate, что используется для инвентарных очередей.

Диагностические наблюдатели не используют адреса относительно `mss32.dll`, не закрепляют её версию и не читают её нижнюю RakPeer-очередь или notification-флаг. Мод может менять поведение за нативной границей либо изменять точки перехвата, поэтому одинаковый EXE не гарантирует одинаковую полноту трассы со всеми модами. Отсутствующий callback — пробел покрытия, а не доказательство потери сообщения.

## Собрать полезную пару логов

1. Включите трассировку **у обоих участников** до подключения: на хосте и присоединяющемся клиенте. Если оба процесса работают из одной папки, различайте их по PID в имени файла. Если на разных компьютерах — явно подпишите, какой файл откуда.
2. Не меняйте остальные настройки для этого прогона. Зафиксируйте версию и SHA256 `C4dll-R.dll`, `Discipl2.exe`, `mss32.dll`; сохраните рядом отдельные копии `C4menu.ini`, `ddraw.ini`, `Disciple.ini`, `C4plugins.ini`. Это нужно для сопоставления условий, а не для замены мода.
3. Запишите, кто хост, кто атакующий, чей ход, какой сейв/сценарий и приблизительное местное время начала проверки с часовым поясом.
4. Для переноса предметов: откройте нужный инвентарь, дождитесь спокойного экрана и выполните заранее выбранное одно действие. Укажите предмет/направление и был ли это первый перенос после открытия. Затем отдельно можно повторить действие для сравнения «первый/последующие». Не смешивайте в одной отметке десять разных кликов.
5. Для боя: запишите момент начала проблемы, PvE/PvP, остаток таймера, кто включил автобой и какой игрок перестал получать управление. Не пытайтесь разблокировать зависание дополнительными переключениями ради трассы.
6. Если проблема возникла, по возможности оставьте процессы как есть хотя бы пару секунд и скопируйте **оба CSV**, соответствующие этому запуску. Writer допускает чтение открытого файла. Не закрывайте и не перезапускайте игру только ради сохранения лога; сначала сохраните уже записанное и сообщите состояние.
7. Передавайте CSV вместе с описанием и сохранёнными конфигурациями по согласованному приватному каналу. Отметьте, скопирован ли лог из живого процесса или после выхода, и были ли ручные действия после сбоя.

Для этого протокола **не нужны debugger attach, остановка потоков, full dump или ручной PostMessage**. Длительная остановка сетевого процесса может сама вызвать timeout/disconnect и изменить наблюдаемую картину. При отдельной необходимости такой захват согласуется отдельно, а не добавляется автоматически к этому тесту.

Данные могут успеть заполнить лимит до редкого зависания. Проверяйте наличие `#stop,reason=cap` и размер логов; если лимит уже достигнут, этот процесс больше не пишет трассу. Автоматического перевыпуска файла и кольцевого хранения на диске нет. Начать новый файл можно новым согласованным запуском, но не рестартом уже пойманного ценного зависания.

## Что находится в CSV

Начальные строки с `#` — метаданные. Далее заголовок:

```csv
seq,qpc,tick,tid,event,object,a,b,c,d
```

| Поле | Смысл |
|---|---|
| `seq` | Номер попытки записи внутри процесса; пропуски возможны при потере событий |
| `qpc` | Полный 64-битный QueryPerformanceCounter, основная шкала для коротких интервалов |
| `tick` | Сырой 32-битный GetTickCount, миллисекунды; это не виртуальные игровые тики |
| `tid` | Windows thread ID, десятичное число |
| `event` | Код события из таблиц ниже, десятичное число |
| `object,a,b,c,d` | Пять `uintptr_t`, записаны как `0x...`; значения могут быть адресами, IDs, флагами либо числами |

Метаданные: `#schema,C4trace,1`, `#pid`, `#qpc_frequency`, `#start_utc`, `#start_qpc`, `#record_capacity`, `#file_cap_bytes`, предупреждение о влиянии диагностики. Интервал внутри процесса вычисляется как `(qpc2-qpc1) * 1000 / qpc_frequency` миллисекунд. Порядок строк между потоками не обязан совпадать с числовым порядком `seq` или `qpc`: потоки могут по-разному добраться до буфера. Сопоставляйте также `tid`, объект и параметры.

Адреса не являются стабильными IDs между процессами. QPC разных компьютеров нельзя напрямую вычитать. `start_utc` помогает ориентироваться по времени, но не доказывает точную синхронизацию часов двух машин. Обычный `tick` и `MSG.time` требуют учёта 32-битного переполнения.

Строки состояния:

```text
#status,lock_drops=...,buffer_drops=...,written=...
#stop,reason=...,win32_error=...,lock_drops=...,buffer_drops=...,accepted=...,written=...,unwritten=...
```

`lock_drops` — попытка неблокирующего lock не удалась; `buffer_drops` — активный буфер заполнен. `accepted` — принятые в память записи, `written` — записанные целые строки, `unwritten` — принятые, но не записанные к остановке writer. `reason=cap` означает ограничение объёма; `io_failure` — ошибку вывода; `low_disk_or_disk_query_failure` — мало места либо ошибку проверки диска. `test_stop` относится только к синтетической тестовой программе, не к игровому API.

| 21 | FEATURE_WND, HWND | message ID | wParam | lParam | 0 |
| 22 | NATIVE_WND_ENTER, HWND | message ID | wParam | lParam | 0 |
| 23 | NATIVE_WND_RETURN, HWND | message ID | wParam | lParam | 0 |
| 40 | MANAGER, EXE singleton object | адрес refcount | refcount | стадия | 0 либо exception code |

RAW/MAPPED — до/после уже существующей обработки `HandleMessage`, а не до/после сетевой десериализации. `PeekMessage` с `PM_NOREMOVE` может несколько раз наблюдать один и тот же элемент; он не обязательно вынут из очереди. При отрицательном результате GetMessage записывается та же стадия с `obj=0,a=0,b=result,c=remove,d=LastError`; это ошибка API, не обычный MSG.

Post observer стоит на **импорте EXE**, а не на всех вызовах PostMessage всех DLL. Он фиксирует зарегистрированные сообщения `>=0xC000`. Для окон/Get/Peek дополнительно выбраны WM_TIMER, мышиные down/up/double-click, WM_ACTIVATEAPP и WM_KEYDOWN только A/F8. Номер `0xC28B` из прежнего расследования не следует зашивать в анализ нового запуска: зарегистрированные IDs назначаются Windows. При наличии event 2 с `b=1` используйте его `a`.

Event 23 означает только, что вызванный из wrapper исходный WndProc вернулся. Он **не доказывает**, что нужный MSS callback действительно был найден/вызван, нижняя очередь RakPeer вычитана или `m_packetNotificationSent` сброшен. Никаких MSS-полей reset/queue-depth эта трасса не читает. Аналогично `PostMessageA=TRUE` не означает, что получатель обработал сообщение. Успешный WinAPI-вызов может оставить прежний LastError: ненулевой `c` у event 4 сам по себе не равен ошибке, если `b!=0`.

MANAGER доступен только после exact-EXE проверки; `0xFFFFFFFF`/exception требуют проверки доступности снимка, а не трактовки как корректного refcount.

## События часов, ожиданий и вывода

| Event | Название / obj | a | b | c | d |
|---:|---|---|---|---|---|
| 30 | CLOCK, caller | реальный timeGetTime | виртуальное игровое время | factor, где 10 = 1.0× | 0 |
| 31 | WAIT, obj=0 | длительность в QPC ticks | настроенный tickLength, ms | 0 | 0 |
| 32 | WAIT_SUMMARY, obj=0 | число ожиданий | сумма QPC ticks | максимум QPC ticks | tickLength, ms |
| 50 | SURFACE, surface pointer | caps | flags | last_flip_tick | last_blt_tick |
| 51 | UPLOAD, primary surface | 0 | 0 | 0 | 0 |
| 52 | SWAP_ENTER, primary surface | 0 | 0 | 0 | 0 |
| 53 | SWAP_RETURN, primary surface | 0 | 0 | 0 | 0 |
| 54 | RENDER_START, obj=0 | 0 | 0 | 0 | 0 |
| 55 | SURFACE_WAKE, surface pointer | 0 | 0 | 0 | 0 |

Frame/surface события подробны в двухсекундном окне после мышиного ввода либо F8, а не постоянно. `RENDER_START` не требует этого окна, но может произойти до поздней инициализации трассы. CLOCK вне активного окна прореживается до изменения factor либо примерно 250 ms; WAIT пишет подробности в активном окне или при длительности от 50 ms, плюс сводку примерно раз в 250 ms на поток. Не нажимайте F8 вслепую ради маркировки: клавиша всё ещё передаётся игре, диагностика её не потребляет.

Полезная цепочка первого кадра: вход команды/notify → SURFACE → SURFACE_WAKE → UPLOAD → SWAP_ENTER/RETURN. `SWAP_RETURN` означает возврат CPU из SwapBuffers, **не** аппаратную отметку показа пикселя на мониторе. Все `a..d` имеют ширину указателя процесса; у x86 длительные суммарные QPC значения в WAIT/WAIT_SUMMARY могут усекаться до 32 бит. Для точной хронологии используйте полные `qpc` строк.

### Передача событий hidden server / FastAI

| Event | Название / obj | a | b | c | d |
|---:|---|---|---|---|---|
| 70 | FASTAI_DISPATCH_ENTER, HWND | message ID | wParam | lParam | context |
| 71 | FASTAI_DISPATCH_RETURN, HWND | message ID | LRESULT | LastError исходного вызова | context |

`context & 0x7F` — источник: `0=внешний dispatch`, `1=class fallback`, `2=сообщение из очереди`, `3=synthetic timer при пустой очереди`, `4=synthetic timer после вычитанного WM_TIMER`. `context >> 8` — глубина вложенности для текущего TID; `context & 0x80` у RETURN отмечает abnormal unwind. Сопоставляйте вход/выход по TID, HWND, message и depth.

Эта точка наблюдает все передаваемые через неё server-события при включённой трассе, не только двухсекундное окно ввода. Наблюдатель не создаёт synthetic timer: он лишь маркирует уже существующую ветку FastAI. RETURN — возврат либо выход при unwind, а не подтверждение обработки сетевого пакета. Числовые параметры hidden-server сообщений следует считать диагностическими данными так же, как остальной CSV.

## События инвентаря и native command queue

Эти наблюдатели устанавливаются только для подтверждённого Win32 `Discipl2.exe`: 4 187 648 байт, SHA256 `1375CDEF09EC470EE64FE5693FB734D7C69FB215212311D997F792B258A642EB`, ожидаемый loaded image и сигнатуры hook-sites. Несовпадение оставляет неизвестный участок нетронутым; изменённая точка пропускается отдельно, переход по JMP мода не разыскивается. Часть наблюдателей может оказаться недоступна. Это проверка игрового EXE, **не фиксация версии mod/mss32**.

| Event | Название / obj | a | b | c | d |
|---:|---|---|---|---|---|
| 100 | READY, EXE base | маска установленных seams | ingress address | native Push address, справочно | 0 |
| 101 | UNAVAILABLE, base либо site | причина | mask либо Win32 error | mask при transaction error | 0 |
| 102 | IDENTITY, EXE base | exact: 1/0 | ожидаемый размер EXE | 0 | 0 |
| 110 | SEND_ENTER, sender self | from ID | to ID | item ID | flags |
| 111 | SEND_LEAVE, sender self | from ID | to ID | item ID | flags |
| 112 | SEND_CALLER, sender self | caller | from pointer | to pointer | item pointer |
| 114 | INGRESS_ENTER, command queue | message pointer | message vtable | player ID | command sequence |
| 115 | INGRESS_LEAVE, command queue | message pointer | callback result | queue length после вызова | queue flags |
| 116 | INGRESS_SENDER, command queue | sender network ID | CNMMap pointer | caller | 0 |
| 118 | APPLY_ENTER, command queue | front message pointer | message vtable | player ID | command sequence |
| 119 | APPLY_LEAVE, command queue | entry-time message pointer | queue length после вызова | queue flags | 0 |
| 120 | NOTIFY_ENTER, data cache | changed object pointer | object ID | object vtable | caller |
| 121 | NOTIFY_LEAVE, data cache | entry-time object pointer | entry-time ID | entry-time vtable | caller |
| 122 | QUEUE_BEFORE, command queue | message pointer | queue length | queue flags | front message pointer |

READY mask: `1=send`, `2=ingress callback`, `4=apply`, `8=object notification`. UNAVAILABLE reasons: `1=unsupported EXE`, `2=modified site`, `3=Detours transaction failure`, `4=unsupported architecture`. Если весь callback отсутствует, его событий закономерно нет; это не доказательство потери сетевого сообщения.

Queue flags: `processingCommand | (commandUpdateApplied << 8) | (started << 16)`. `0x80000000` означает недоступное чтение flags. Защищённые 32-битные чтения других полей при неудаче возвращают 0; этот 0 сам по себе не подтверждает реальную пустоту/нулевой ID. Здесь наблюдается **native CMidCommandQueue2**, не нижняя `CNetCustomPeer::packetReturnQueue`.

Ingress — `CNMMap::queueMessageCallback` перед native `Push`; уже установленный mod-detour самого Push сохраняется. `INGRESS_LEAVE result=true` означает возврат callback, **не** принятие команды сервером и не гарантию помещения в очередь. `APPLY_LEAVE` означает возврат ApplyCommandUpdate, не гарантию финальной перерисовки списков. `NOTIFY_LEAVE` использует снимок входных полей, поскольку подписчики могли заменить или удалить объект.

## Ограничения, сохранность и приватность

- Фиксированная память: два буфера по 8192 записи, всего 16 384. Производитель делает QPC/raw tick/TID и POD-копию через try-lock. На этом пути нет файлового вывода, форматирования строк, Sleep или ожидания lock. `GetLastError` сохраняется.
- Writer проверяет/вычитывает буфер примерно каждые 250 ms; FlushFileBuffers выполняется только writer, примерно раз в секунду успешных циклов. Загрузка диска может увеличить задержку. Нельзя обещать, что пауза ровно в две секунды гарантирует запись каждой последней строки.
- Один файл на процесс, жёсткий предел **32 МиБ**, без перезаписи и ротации. При нехватке **64 МиБ** свободного места, ошибке проверки диска или IO writer прекращает запись. Если сам файл уже нельзя дописать, сообщение ошибки остаётся только в OutputDebugString; наличие `#stop` не гарантируется при IO failure.
- Нет синхронного shutdown/drain из игрового callback. При резком завершении и даже при обычном выходе последние записи в памяти могут не попасть в CSV. Отсутствие `#stop` не доказывает crash. Включённый модуль закреплён до конца процесса для безопасности worker. Подтверждённые переключение диагностики и общий сброс используют `ExitProcess` текущего клиента, как быстрый выход враппера, а не `TerminateProcess`; это не означает автоматическое сохранение игры, сохранение всего CSV-хвоста или корректное завершение матча для остальных участников.
- Наблюдатели не посылают/retry сообщения, не снимают паузу, не исправляют MSS-флаг, не меняют порядок игровых команд, CPU affinity, приоритеты, `maxgameticks` или коэффициенты времени. Но включение устанавливает диагностические pass-through IAT/EXE seams; это не «вообще ноль вмешательства». Первоначальная exact-EXE проверка читает и хэширует EXE; наблюдаемые с её помощью игровые действия следует начинать после завершения старта.
- Нет записи текстов чата, произвольных клавиш, содержимого инвентарных описаний или полных сетевых пакетов. Тем не менее CSV содержит PID/TID, UTC-время, адреса, игровые/object/player IDs, координаты/параметры выбранных сообщений и маркеры A/F8. Это диагностические данные, а не обезличенная статистика. Конфиги и соседние игровые логи могут содержать больше персональных данных; проверьте их перед отправкой и не публикуйте автоматически.

## Как интерпретировать результат

Для исследователя есть read-only анализатор (Python 3.7+, без внешних библиотек):

```powershell
python c4ddraw/tools/analyze-event-trace.py "C:\path\C4trace-....csv"
python c4ddraw/tools/analyze-event-trace.py "C:\path\C4trace-....csv" --json
```

Путь в примере заменяется реальным CSV. Скрипт не подключается к игре и не меняет лог: выдаёт метаданные, счётчики событий, парные длительности Post/native/send/apply/notify по TID и предупреждения о неполноте. Это не автоматический диагноз и не вычисление latency предмета по несопоставленным событиям. Схема остальных событий остаётся доступна в исходном CSV. Синтетические тесты: `python -m unittest discover -s c4ddraw/tests -p test_analyze_event_trace.py`.

| Наблюдение | Допустимый вывод | Что проверять дальше |
|---|---|---|
| POST_ENTER/RETURN есть, GET/PEEK/WND нет | Видна отправка через наблюдаемый EXE import; дальнейшая стадия в трассе отсутствует | drops, cap, PID/TID/HWND, доступность hooks; не объявлять автоматически потерянное MSS-уведомление |
| NATIVE_WND_RETURN есть | Этот WndProc вернулся | Нельзя приравнивать к reset MSS notification flag; для этого нужны отдельные доказательства |
| SEND есть, затем INGRESS значительно позже | Интервал между двумя выбранными границами измерен | Сопоставить обе стороны, IDs/sequence, доступность ingress; не списывать весь интервал на renderer |
| INGRESS/APPLY/NOTIFY быстрые, SURFACE/UPLOAD поздние | Кандидат на задержку интерфейса/публикации кадра | Проверить активное двухсекундное окно и связность именно нужного объекта |
| SURFACE своевременно, SwapBuffers долго возвращается | Измерена задержка CPU внутри границы вывода | Не путать с временем показа на мониторе; сравнить одинаковые условия |
| Есть drops или cap перед проблемой | Трасса неполная | Не выводить причинность из одного отсутствующего события |

Исходные определения: [eventtrace.h](features/eventtrace.h), [eventtrace.cpp](features/eventtrace.cpp), [inventorytrace.cpp](features/inventorytrace.cpp), [timerhost.cpp](features/timerhost.cpp), [c4trace.cpp](features/c4trace.cpp). Синтетические проверки самого recorder запускаются [tests/test-c4trace.ps1](tests/test-c4trace.ps1); они не запускают игру и не доказывают полноту игровых hook-путей.
