# Тестовая обработка пачек сообщений

Изменения находятся только в C4dll-R: MSS не пересобирается и не патчится. Пользователь подтвердил на alpha со сборкой `1.9.0-dev.20260904-batch2` быстрый перенос предметов, сопоставимый с оригинальным адаптером. Это результат конкретного прогона, не универсальная гарантия для всех модов и систем. Устранение редкого зависания автобоя пока не доказано.

## Что меняется

После обычного DispatchMessage враппер может обработать до 32 следующих уведомлений `MIDGARD NETMSG` / `MQ_COMMANDQUEUE2` без промежуточного игрового update/render. Затем выполняется обычное обновление игры. Бюджет пачки — 1 мс с проверками между обработчиками; отдельный долгий обработчик прервать этим лимитом нельзя.

Пачка не перескакивает через ввод, таймеры, сообщения других окон и WM_QUIT. Она останавливается при смене контроллера, модальном переходе, вложенном игровом цикле или изменении состояния окна. Координаты дополнительных MSG проходят обычный mapping враппера ровно один раз.

CPU0, настройка 180 тиков, приоритеты, игровые часы и правила турнирного таймера остаются прежними. Увеличение скорости прохождения очереди не реализовано повышением глобальной частоты игры.

## Переключение

По умолчанию пачки **включены**, даже если ключ отсутствует. Для явной фиксации настройки и записи диагностических логов в существующую секцию `[menu]` файла `C4menu.ini` выбранного тестового инстанса добавляется:

```ini
[menu]
messageBatching=1
netTrace=1
```

Не заменять этим фрагментом весь INI и не создавать дублирующую секцию. Если ключ задан, только точное значение `1` включает пачки; явный `0` или неверное значение выключает. Изменение `messageBatching` вступает в силу при следующем запуске; это не переключатель live. `netTrace` нужен для измерений, а не для работы пачек. Подробности и лимиты логов: [NETWORK_TRACE.md](NETWORK_TRACE.md).

Для контрольного прогона на той же DLL: `messageBatching=0`. Для отката достаточно вернуть `0` и перезапустить согласованный тестовый инстанс. Текущие запущенные игры эта инструкция не изменяет.

При включённой трассе событие `130` подтверждает установку перехвата. `131` означает отказ; само наличие `messageBatching=1` не доказывает, что перехват заработал. Без трассы пока нет отдельного GUI-индикатора установки.

## Не смешивать две проверки

1. Проверить перенос одного первого предмета на одной DLL с `messageBatching=0` и `1`, сохранив одинаковыми MSS, настройки рендера, CPU0 и 180 тиков. Состояние FastAI между этой парой не менять; для начального изолированного сравнения его можно заранее выключить в обоих прогонах.
2. Сравнить click/send → ingress → Apply → OnObjectChanged → frame по двум логам. Номер первого предмета, направление переноса, хост/клиент и открытие инвентаря должны быть одинаковыми. Первая задача — сократить интервал до Apply, а не только повысить FPS.
3. Отдельно проверить FastAI и автобой. FastAI — ускоритель работы ИИ на хосте, а не переключатель обязательного автобоя по нулю таймера. В этой сборке исправлена доставка реальных MSG/TIMERPROC, завершение вложенных вызовов и выход из ускорения при уничтожении окна. Правила блокировки автобоя не менялись.

Нужны оба клиентских CSV. Измерения выполняются по логам; ручные секундомеры не нужны. Трасса влияет на timing, поэтому после сравнения нужны также повторения без неё. Автотесты уже выполнены, но не заменяют сетевую игру с настоящим MSS.

## Границы совместимости

Проверяются SHA256, PE-параметры стабильного `Discipl2.exe` и точные байты участка в памяти. Неизвестный EXE или изменённый соседний код — отказ от установки. Сборка/адреса MSS не используются. Это не обещание совместимости с любым будущим модом, который поменяет сам игровой цикл или начнёт исполнять его из нескольких потоков.

Установка рассчитана на штатный owner UI thread этого EXE. Общий многопоточный hot-patch не реализован; DLL закрепляется в процессе, чтобы установленный переход не остался после её выгрузки. Потоки работающих игр в рамках подготовки этой сборки не останавливались.

Пачки не восстанавливают потерянное уведомление: если в Windows-очереди уже нет нужного сообщения, они не создают его повторно. Связь исторического вечного зависания с этой правкой ещё должна быть подтверждена отдельно.

## Новые события CSV

`object,a,b,c,d` имеют тот же формат, что остальные события C4trace.

| Код | Смысл | Поля |
|---|---|---|
| 130 | Перехват установлен | object=0x562972; a/b=зарегистрированные IDs; c=32; d=1000 мкс |
| 131 | Установка отклонена | a=причина; b/c=контекст ошибки |
| 132 | Начало разрешённой пачки | object=kernel; a=первое сообщение; b=32; c=1000; d=epoch |
| 133 | Дополнительное сообщение извлечено | object=HWND; a=raw message; b/c=wParam/lParam только разрешённых IDs; d=номер extra |
| 134 | Завершение вызова helper | object=kernel; a=число extra; b=причина остановки; c=младшие 32 бита длительности QPC; d=SEH unwind |
| 135 | Первый штатный Dispatch вернулся | object=kernel; a=message; b=depth; c/d=epoch до/после |

Причины `131`: 1 — HWND/поток/EXE/байты не прошли проверку; 2 — регистрация IDs или QPC недоступны; 3 — ошибка Detours; 4 — не x86; 5 — не удалось закрепить DLL.

Причины `134`: 0 — пусто; 1 — лимит количества; 2 — время; 3 — барьер; 4 — смена контекста/неподдерживаемый вход; 6 — ошибка/обратный ход QPC; 7 — голова изменилась между Peek и Remove; 8 — неожиданно извлечён WM_QUIT. Значение 5 зарезервировано, сейчас не выдаётся.

Событие `134` бывает без `132` при раннем отказе и во вложенном вызове: нельзя наивно попарно сопоставлять их как обычный ENTER/RETURN. Полный timestamp `qpc` берётся из стандартной колонки, а не из усечённого поля `c`. Generic analyzer пока выдаёт счётчики этих новых событий, но не готовую причинную оценку ускорения.

Исходные автотесты находятся в репозитории в `c4ddraw/tests`. Полный отчёт: `docs/2026-09-04_reverse-wrapper-batching-implementation-report.md`.
