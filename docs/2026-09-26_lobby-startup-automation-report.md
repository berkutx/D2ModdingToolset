# Автоматический старт двух клиентов через лобби

## Результат и граница проверки

Настоящие лобби-прогоны с обычным и намеренно задержанным джойнером прошли startup-приёмку.
Оба клиента вошли на карту, закрыли штатные начальные диалоги и получили настоящий
`bootstrap operational release`. Отказов ОХ не зафиксировано. Это **не** приёмка
объединения ходов, боёв или всей 18-case кампании: они этим сценарием не выполняются.

Проверяемая DLL — PR11, native source `4e82f6d3`, DebugTest Win32, OH+testdrv:
SHA256 `85f80c73014cff4cc4c7a18b3d07f2ade4bada87b590628c7e40c41703c0c938`.
Перед установкой проверен резерв предыдущей `c7508047` DLL. `DisplayErrors=1`.
Последующие изменения runner/CI не меняют native DLL. Production-исправление
раннего UpdateObj опубликовано отдельно в PR10, `9eedb76c`:
[доказательство и границы исключения](2026-09-26_reverse-oh-initialization-report.md).

## Почему перестали автоматически закрываться окна

**F1 — подтверждено кодом и живым прогоном.** Старый `testdrv/scriptedpopups.cpp`
не удалялся. Новый диагностический lobby-runner не включал его и частично
дублировал обработку окон. Из-за этого джойнер оставался на штатном
`DLG_MESSAGE_BOX` с текстом «Начало задания, день 1».

Runner теперь включает прежний subscriber и использует прежние read-only
наблюдатели его `OBSERVED → CLAIMED → COMMITTED`. Только он вызывает начальные
native callback, однократно, после минимального settle 300 мс. В normal-003
окно дня 1 джойнера закрыто через 313 мс. Подтверждаются стандартные имена
лидеров; никакой текст имени не вводится.

Новый test-only lobby scope отделяет prepared-предложения до карты от начальных
диалогов карты. Только точный CP1251-текст дня 1 с `BTN_OK` допускается для
generic message box; ошибки и неизвестные сообщения не закрываются автоматически.
Старый TCP/IP-режим сохранён. DelayedJoin выпускает окна хоста по точным
PID/appearance/owner, затем отдельно джойнера, не посылая хосту повторный release.

**F2 — исправлены ошибки orchestration, не игрового протокола.**
Несколько Node в PATH теперь не склеиваются в один исполняемый путь. При
повторном PID старые байты лога отсекаются сохранённой границей перед запуском;
исходные логи не удаляются. Начальный rebind комнаты при входе другого игрока
ожидается одним существующим `invoke-when-ready`, а не повторными нажатиями.

## Живые доказательства

Артефакты локальны, не публикуются вместе с исходниками. Окна управляются только
native testdrv/relay, без computer-use, action JSON и решений LLM между шагами.
Каждый прогон создаёт свою casual-подготовку и закрывает её без результата/PTS.

## Повторение и регрессии

[Команды, конфигурация и точная граница startupAcceptance](TEST_HARNESS.md#полностью-автоматическая-подготовка-через-сайт).
Аккаунты/пароли передаются через окружение, не записываются в логи или исходники.
Каждому запуску нужен новый каталог артефактов.

Пройдены: 108 relay-тестов, 91 offline-проверка runner, 16 API-проверок и
извлечённая настоящая native state machine popup subscriber с подставленными
платформой/UI/SEH. Native DebugTest сборка: 0 ошибок, прежнее LNK4075.
Offline-проверки включены в harness-only CI; локальный PASS не выдаётся за
завершённый удалённый CI. Production PR10 не включает этот игровой харнес.
