# Подготовленные матчи: клиент MSS

Клиент принимает предложение создать матч или приглашение войти в готовую комнату
только от аутентифицированного лобби и только для текущего аккаунта.
Нового capability нет: сообщение добавлено в конец расширений (`ID_USER_PACKET_ENUM + 16`),
старые клиенты его игнорируют. Штатные ручное создание, загрузка и `111` сохраняются.

## Согласие и генерация

Предложение ждёт свободного `CMenuCustomLobby`: без игровой сессии, перехода,
подключения, окна пароля, помощи или другого верхнего интерфейса. Native Yes/No
показывает название и рейтинг, по строке на участника с расой/лордом и отметкой
хоста, первый ход и явно изменённые условия. Имя Lua-примера и техническое пояснение
о выборе версии не повторяются. Из серверной сводки убирается только точно
совпадающее перечисление этих же условий; ставки и неизвестный текст сохраняются.
Сначала весь текст с коротким вопросом «Сгенерировать карту?» проверяется по реальным
размерам `TXT_INFO` и native метрикам шрифта: без лишнего счётчика `(1/1)` и
искусственного ограничения страницы в 1024 байта. Только не поместившиеся условия
разбиты на страницы; никакое продолжение не отбрасывается. Только последнее «Да»
разрешает генерацию.
«Нет» откладывает попытку; повторная доставка той же попытки не открывает окно снова.

После согласия выбирается последняя локальная версия семейства шаблона из
неизменяемого каталога запуска; для нераспознанной версии нужен точный basename.
MD5 примера сайта не ограничивает выбор локального Lua. После выбора проверяются
параметры и число игроков; несовместимые значения не округляются и не заставляют
выбирать старую версию. Каталог сохраняет исходные байты Lua, hash и разобранные defaults. Hash считается
по binary bytes, включая CRLF. RSG предоставляет только path-reader настроек:
при startup исходник читается до и после этого reader; изменение файла отвергается.
Возврат в меню не перечитывает шаблоны. Добавленный или заменённый Lua требует
перезапуска клиента. Автоматического скачивания и выполнения серверного Lua нет.

Обычный генератор получает проверенные настройки и сохранённый source. Preview,
Retry, Accept и Cancel используют существующий GUI; повторная попытка заново
исполняет `getContents`, не переиспользуя ранее выпавшее содержимое. Это первая
генерация, а не команда рестарта. Accept сохраняет тот же рецепт для последующего `111`.

Согласованная раса хоста становится первой в native списке setup. Тип лорда
переключается существующим callback `BTN_LORD`, с сохранением выбранного портрета
и проверкой AnsStartInfo. Проверены native пути Russobit; для неподтверждённых
версий автоматическая генерация завершается явной ошибкой. Выборы джойнеров
автоматически не меняются. [Доказательство](2026-09-20_reverse-prepared-native-report.md).

## Приглашение в созданную комнату

Core предлагает вход только после реального создания комнаты хостом, с учётом
разрешения приглашений в профиле участника. Предложение не является командой входа:
MSS ждёт свободного лобби без игровой сессии, перехода, помощи, пароля или иной
модалки. Это работает для уже открытого лобби, нового login и возврата из игры.
До первого показа запрашивается свежий список комнат; комната ищется по ID и хосту
и должна иметь свободное место. Ещё не загруженный список не означает отказ:
после 15 секунд без результата запрос повторяется, ожидание в игре не истекает.

Native Yes/No показывает название матча и хоста. «Нет» завершает именно это
приглашение без входа. Последнее «Да» после всех страниц запускает ещё один свежий
поиск, затем общий с ручной кнопкой Join путь. Проверки FilesHash, TemplateHash,
наличия Lua и пароля остаются прежними, включая обычные сообщения об ошибках.
Раса, лорд и портрет гостя выбираются штатно; restart-путь не используется.
`Accepted` означает согласие и начало обычного входа/окна пароля, **не** успешный
ответ асинхронного JoinByFilter и не подтверждённое участие в комнате.

`Accepted`, `Declined`, `Unavailable` запоминаются по полной identity, room ID и
получателю; повторный logout/login в том же процессе не сбрасывает последние
512 терминальных ответов. Другой аккаунт или новая попытка не наследуют ответ.
Потеря соединения очищает очередь и инвалидирует callback старого окна; core
может доставить ещё не решённое приглашение после нового login. `JoinCancel`
убирает ожидающее приглашение или только принадлежащее ему окно на безопасной
точке главного потока. Поздний callback не начинает вход; уже начатая обычная
сессия не прерывается.

### Расширение wire v1

Старые операции `Offer=0`, `Status=1`, `Cancel=2` неизменны. Новые операции
добавлены в конец того же packet ID; дополнительного capability нет. Все числа
big-endian, строки имеют длину u16 в байтах. Identity: preparationId, gameId,
attemptId — по 1–64 ASCII `[A-Za-z0-9_-]`, затем ненулевая revision u32.
Room ID — u32: **0 допустим**, `UINT32_MAX` отвергается.

| Операция | Направление | Поля после version=1 и opcode |
| --- | --- | --- |
| JoinOffer=3 | core → MSS | identity, room ID, host UTF-8 (1–192 байта), title UTF-8 (0–256), recipient UTF-8 (1–192, обязателен) |
| JoinStatus=4 | MSS → core | identity, room ID, state u8, detail (0–128 байт) |
| JoinCancel=5 | core → MSS | identity, room ID |

JoinState: Received=0, Busy=1, Prompt=2, Accepted=3, Declined=4, Unavailable=5.
Максимальный payload без packet ID: JoinOffer 854, JoinStatus 339, JoinCancel 208
байт. Усечения, неизвестная версия/операция, лишние байты и control characters
отвергаются. MSS также требует точное совпадение recipient с текущим аккаунтом;
host не может приглашать сам себя. Core проверяет auth GUID, разрешение профиля,
связанную room instance, актуальность identity и возможность войти в комнату.

## Идентичность и отмена

Каждая попытка имеет preparationId, gameId, attemptId и revision. Все поля строк
имеют bounded length, integers — big-endian, лишние байты и неизвестные параметры
отвергаются. Native race IDs: Empire0, Undead1, Legions2, Clans3, Elves5;
wire random=-1 отдельно переводится в RSG Random. Типы лорда: Mage0, Warrior1, Thief2.

`PreparationId`, `GameId`, `PreparationAttemptId`, `PreparationRevision` передаются
как отдельные room properties. Данные не связываются по сходству никнеймов и времени.

Cancel ставит запрет Accept/CreateRoom на главном потоке. После этой гарантии MSS
отправляет Canceled ACK, не дожидаясь тяжёлой геометрии генератора. До завершения
старого worker и очистки preview новая попытка остаётся в очереди. Если CreateRoom
уже отправлен, MSS ждёт действительного ответа и не прерывает созданную игру;
лобби получает RoomCreated либо ошибку. RoomsPlugin и статусы используют один
RELIABLE_ORDERED channel 0. Modal callback хранит только epoch, не указатель на меню.

## Проверки

### Совместимость онлайн-клиентов

После успешного Lobby2 login MSS отдельно сообщает существующий `FilesHash`, ещё
до создания комнаты или подключения к ней. Пакет `ID_USER_PACKET_ENUM + 17`:
после ID ровно 33 байта — version `1` (u8), затем 32 ASCII lowercase hex без
длины, ника и завершающего нуля. Получатель — только GUID текущего залогиненного
лобби; аккаунт определяет core по соединению. Старые серверы игнорируют расширение.

Состав файлов и алгоритм прежние: `mss32.dll`, прежний набор Globals и Scripts с
теми же исключениями. Путей и списка файлов в пакете нет. Хеш вычисляется одним
фоновым worker; пути собираются на главном потоке, worker владеет только их копией.
Login не ждёт чтения и хеширования файлов. Host/join при необходимости ждут тот же
future в существующем wait-dialog и используют тот же кэш, без второго вычисления.
Уничтожение service присоединяет worker после удаления UI callbacks.

Повторный login того же service снова отправляет кэш. Logout/disconnect отменяют
публикацию; ошибка вычисления означает неизвестную совместимость, не пустой или
нулевой hash. Login и фон не повторяют неудачное вычисление автоматически.
Следующий явный host/join может повторить завершившееся неудачей вычисление;
готовый успешный кэш и ещё работающий worker не сбрасываются. Успешный результат
такого ручного повтора снова публикуется для текущего залогиненного соединения.
После успешной постановки RELIABLE_ORDERED-пакета повторов нет;
локальная ошибка отправки допускает максимум три попытки с интервалом 1 секунда.
Существующие проверки совместимости при входе в комнату не изменены.

`tests/run-client-compatibility.ps1 -OutputDirectory <каталог>` проверяет wire,
неблокирующий polling, единый future/cache, ручное восстановление после ошибки без
фонового retry-loop, teardown и границы повторов отправки.

### Подготовка и генерация

- Пересечение Cancel с уже отправленным CreateRoom не пропускает обязательного
  лорда: успешное создание снимает отложенный canceled и завершает штатный Setup.
  Поздняя отмена во время Setup сохраняет комнату и не прерывает этот выбор.
- `tests/preparedmatchprotocol_test.cpp`: golden wire/status, truncation каждого
  байта, version/length/trailing bytes, категории, signed custom values и ключи.
- `tests/preparedmatchsettings_test.cpp`: defaults, неизменность snapshot, host-first,
  clans/undead mapping, random, диапазоны и шаги custom spins, число игроков.
- `tests/preparedmatchlifecycle_test.cpp`: cancel ACK до создания, safe-point для
  генерации/CreateRoom, поздняя отмена созданной комнаты и повторная отмена при возврате;
  join idle/busy gate, свежие комнаты до показа и после «Да», терминальные ответы.
- `tests/preparedmatchtext_test.cpp`: компактный текст, native race/lord IDs,
  сохранность ставок и нестандартных условий, точное удаление повторов, проверка
  целого текста до пагинации и побайтовая сохранность продолжения. Инъекция метрик
  в консольном тесте не заменяет проверку native шрифта в игре.
- `tests/run-prepared-match-protocol.ps1`: запускается из MSVC x86 developer shell;
  `OutputDirectory` обязателен, `DependenciesRoot` включает дополнительные RSG settings tests.
  Необязательный `CoreRoot` дополнительно компилирует и запускает настоящий core
  `preparedmatch_test`, затем `preparedmatchjoin_crosswire_test.cpp` с обоими кодеками.
- Существующий `run-scenario-template-recipe.ps1` проверяет fresh Lua state и
  входы `getContents`, в том числе реальные локальные Outrunner при указании путей.

Автоматические консольные проверки не заменяют игровой прогон. Перед выпуском
нужны два клиента с `DisplayErrors=1`: занятое меню, Yes/No, длинные условия,
отсутствующий/hash-mismatch Lua, Retry/Cancel, Cancel↔Accept race, native портрет,
вход джойнера, завершение и `111`. Изменять установленную DLL без согласования нельзя.
Короткие шаги и критерии остановки — [ручная приёмка](PREPARED_MATCHES_ACCEPTANCE_RU.md).
