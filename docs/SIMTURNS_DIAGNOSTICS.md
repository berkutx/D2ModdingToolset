# Диагностика первой остановки ОХ

Это сбор диагностических данных, **не исправление отказа**. Проверки ОХ,
результаты native dispatch, wire-контракт и остановка после Abort не меняются.
Установка DLL и повтор в двух настоящих клиентах выполняются отдельно от сборки.

## Воспроизвести и сохранить лог

1. На обоих клиентах использовать одну диагностическую сборку. Перед заменой
   DLL закрыть клиентов и сохранить проверенный резерв прежней DLL.
2. Оставить `DisplayErrors=1` в секции `[Disciple]` действующего `Disciple.ini`.
   Перезапустить клиентов после установки DLL; остальные настройки не менять.
3. Повторить подготовку с ОХ: хост создаёт комнату, второй игрок входит.
   Записать время первого окна ошибки и кто был хостером. Не продолжать карту
   после сообщения об остановке ОХ.
4. Сохранить `mss32.log` обоих клиентов до следующего запуска. Если два процесса
   используют одну папку, строки могут перемешиваться: сопоставлять по `pid`,
   `room`, `epoch` и `role`, не только по времени или позиции в файле.

Из каталога игры можно прочитать диагностические строки без изменения лога:

```powershell
Select-String -LiteralPath .\mss32.log -SimpleMatch '[simturns-diag]'
Get-FileHash -LiteralPath .\mss32.dll -Algorithm SHA256
```

## Что означают записи

| Запись | Содержимое и назначение |
| --- | --- |
| `arm` | PID, комната, эпоха, роль, день объединения; отдельно результаты подготовки port и native session |
| `native_failed` | Ticket и endpoint, класс/размер/type пакета, sender/receiver DPID, поток RX, receive-site/replay, политика и фактический handler count |
| `local_abort` | Локальный первый отказ адаптера: код Abort и внутренняя причина до отправки на сервер |
| `port_fault` | Первая причина port, включая отказ до стратегического `start`; поколение и `started` фиксируются под mutex |
| `remote_abort` | Abort получен от сервера; это не доказательство, что данный клиент был инициатором |

`dispatched=true`, `policy=pass`, `handler_count=0` означает, что штатный
диспетчер был вызван и вернул нулевой счётчик обработчиков. Это **не** код
успешности отдельного обработчика. `policy=drop`, `dispatched=false` означает
отклонение до native dispatch; ноль в `handler_count` в этом случае не измерен.
Consume остаётся Filtered, Defer сохраняет ticket до replay — эти пути не
переименованы в успешный native dispatch и не получают новых подтверждений.

Диагностика не пишет тела пакетов, чат, пароли или токены. Имя класса копируется
до native dispatch, ограничено 36 байтами, управляющие байты заменяются на `?`.
Очередь UI владеет копией метаданных, а не указателем на уже обработанный buffer.
Обычный успешный поток пакетов не логируется этим механизмом.

## Проверить реализацию

В x86 Developer PowerShell из корня репозитория:

```powershell
./tests/run-simturns.ps1 -OutputDirectory ./artifacts/oh-first-fault-tests
```

Evidence → Finding → Path:

- **E1:** `simturns_lobby_port_test.cpp`, `firstFaultDiagnostics`: первый prestart
  отказ, reentrant callback, исключение диагностического sink, смена поколения,
  stop/quiesce и освобождение callback. **F1:** диагноз доступен до регистрации
  стратегических callbacks, не заменяется повторным fault и не подавляет terminal.
- **E2:** `simturns_native_receive_diagnostic_test.cpp`: фиксированная граница
  имени, отсутствие NUL, управляющие байты, изменение исходного buffer, копия
  метаданных. **F2:** диагностике не требуется читать пакет после его обработки.
- **P1:** `stageNativeReceive` сохраняет header → receive-hook дописывает
  фактические DPID/политику/счётчик → `NativeCompletion` переносит копию на UI →
  первый Failed записывается до прежнего Abort. E1/E2 проверяют отдельные части;
  полная native сборка проверяет MSVC/SEH, но не заменяет игровой прогон.

Точный пакет и первичная причина конкретного игрового отказа определяются только
после воспроизведения. Отсутствие строки само по себе не доказывает отсутствие
ошибки: возможны старая DLL, потеря записи при аварийном завершении или сбой I/O.
