# Контракт сервера лобби для ОХ

Статус: спецификация для реализации серверного адаптера. Серверная реализация и
живая приёмка нового транспорта не входят в этот клиентский PR. Нельзя включать
ОХ в опубликованной комнате, пока сервер не реализует весь протокол.

## Допустить комнату к запуску

Существующий capabilities exchange получает независимый бит `0x2` — ОХ.
Бит рестарта `0x1` сохраняется. Клиент объявляет `0x2` только при включённой сборке
ОХ и прошедшей проверке точного EXE/игровых точек подключения.

Сервер обязан проверить обоих участников, две человеческие стороны, новую карту
с первого дня, неизменность состава/ролей и допустимый день объединения.
Room property `SimultaneousTurns` — явный boolean: `SimultaneousTurnsDays=0`
не отличает выключенные ОХ от ОХ без объединения. Дни `2..30` допустимы, `1` — нет.
Локальная настройка видимости GUI не является сетевым разрешением.

Перед стартом сервер назначает неповторяющуюся ненулевую `epoch` и отправляет
`Arm` обоим клиентам. До обоих положительных `ArmAck` нельзя разрешать штатный
Start, prepared Launch или restart Launch. Клиентский старт также проверяет
готовность адаптера, но эта проверка не заменяет серверную авторизацию.

Роль назначается по реальному участию в комнате, не по PID/role hint из локального
рилея. Клиент сравнивает роль с созданной native session. Неподдерживаемый клиент
не должен незаметно запускать ОХ-комнату как обычную.

## Передавать управляющие сообщения

Используется существующее аутентифицированное SLikeNet-соединение с лобби:
`ID_USER_PACKET_ENUM + 18` (`ID_LOBBY_SIMULTANEOUS_TURNS`). Старые ID не смещаются.
Проверяется GUID действующего сервера и состояние login. Нельзя принимать эти
сообщения от другого игрока, даже если payload содержит правильный roomId.

Управляющие и соответствующие игровые сообщения идут `RELIABLE_ORDERED` по
одному ordering channel `0`. Смена HIGH/MEDIUM priority не заменяет этот порядок.
Нельзя поставить сообщения в разные каналы и восстанавливать порядок задержками.

После ID идёт следующий envelope; все многобайтовые поля unsigned little-endian:

| Поле | Размер | Условие |
| --- | --- | --- |
| version | u8 | Ровно `1` |
| operation | u8 | Arm=0, ArmAck=1, Frame=2, Abort=3 |
| roomId | u32 | ID текущей Rooms-комнаты; `0` допустим |
| epoch | u32 | Ненулевой, возрастает на соединении, не переиспользуется |

| Операция | Направление | Тело после 10 байт заголовка |
| --- | --- | --- |
| Arm | Сервер → клиент | role:u8 (1 host, 2 join), mergeDay:u32 (0 либо 2..30) |
| ArmAck | Клиент → сервер | status:u8 (0 accepted, 1 rejected) |
| Frame | Оба | Ровно один полный v8 frame, включая length prefix |
| Abort | Оба | reason:u16 |

Abort reasons: 1 Protocol, 2 LocalFailure, 3 Disconnected, 4 RoomLeft, 5 RoleMismatch.
Для каждого типа длина точная; усечённые поля, лишние хвосты, неизвестная версия,
role/operation и недопустимые значения отвергаются. Frame максимум 65 540 байт.
Размер сообщения с ID и envelope — максимум 65 551 байт.

`Arm` заменяет транспортный handshake локального pipe, но не игровой bootstrap.
Он приходит после создания текущей native session (и завершения старого teardown),
до первого BeginTurn/TurnInfo новой карты; Arm не ожидает native-apply barrier.
`Hello`, `HelloAck`, `Goodbye` локального транспорта через Frame не используются.
ArmAck подтверждает готовность адаптера, а не загрузку карты.

## Сохранить v8 без переизобретения игрового протокола

Полный frame: `length:u32`, `op:u16`, `flags:u16`, payload.
`length = 4 + payload.size`, flags=0, length в пределах `4..65536`.
Вложенные кадры, несколько кадров за envelope и хвосты запрещены.

В таблице ниже все поля payload — u32, кроме Error. Порядок полей фиксирован.
`epoch` и `actionId` ненулевые, без переполнения; lease ненулевой у выданных ходов
и EngineAction kind 1/2, но равен нулю у kind 3..6. Native day не превышает
`0x7fffffff`. Player handle — фактический игровой идентификатор, не GUID/имя.

| op | Имя | Payload / направление |
| --- | --- | --- |
| 0x0007 | LocalPlayerHandle | handle; клиент → сервер |
| 0x0008 | SessionPlan | epoch, mode, hostHandle, joinHandle, mergeDay, hostLease, joinLease; сервер → клиент |
| 0x000b | SessionActivated | Пусто; клиент → сервер |
| 0x000c | BootstrapBeginTurnApplied | joinHandle, day=1; join → сервер |
| 0x000d | BootstrapComplete | joinHandle, day=1; join → сервер |
| 0x000e | BootstrapCommitted | joinHandle, day=1; сервер → оба |
| 0x000f | BootstrapCommitApplied | joinHandle, day=1; оба → сервер |
| 0x0010 | BootstrapOperational | joinHandle, day=1; сервер → оба |
| 0x0011 | BootstrapOperationalApplied | joinHandle, day=1; оба → сервер |
| 0x0015 | BootstrapReleased | joinHandle, day=1; сервер → оба |
| 0x1000 | EndTurnObserved | epoch, lease; автор хода → сервер |
| 0x1001 | EngineAction | epoch, actionId, kind, playerHandle, day, lease; сервер → адресат |
| 0x1002 | ActionResult | epoch, actionId, kind, success (0/1); адресат → сервер |
| 0x1007 | EndTurnApplied | epoch, lease; host → сервер |
| 0x1008 | MergeApplied | epoch, actionId; оба → сервер |
| 0x10ff | Error | UTF-8, не более 4096 байт; сервер → клиент |

SessionPlan обязан совпадать с Arm по epoch и mergeDay; mode=1 (Simultaneous).
mode=0 не является способом отката принятого ОХ-сеанса. Handle обоих клиентов
различны. Подтверждения принимаются только от ожидаемой стороны и текущего этапа.

## Провести bootstrap

Сервер привязывает LocalPlayerHandle к авторизованным сторонам, затем:

1. Отправляет SessionPlan хосту; ждёт его SessionActivated.
2. Отправляет SessionPlan join; ждёт его SessionActivated и BootstrapBeginTurnApplied.
3. Просит хост выполнить ApplyTurnStart для join, day=1, с joinLease из SessionPlan
   (не выдаёт новый lease). Ждёт успешный ActionResult
   хоста и BootstrapComplete от join; эти два свидетельства могут прийти в любом порядке.
4. Отправляет BootstrapCommitted сначала join, затем host; ждёт оба CommitApplied.
5. Отправляет BootstrapOperational сначала host, затем join; ждёт оба OperationalApplied.
6. Только теперь отправляет BootstrapReleased сначала host, затем join.

Интерфейс и создание карты не считаются готовыми по одному получению пакета.
MSS выдаёт подтверждения из реальных игровых точек; сервер не синтезирует их.
Ожидание брифинга/человеческого окна не должно превращаться в произвольный короткий
таймаут загрузки. Для уже выданных машинных этапов используются явные watchdog.

## Продвинуть отдельный ход

У каждой стороны свой субъективный день и выданный сервером lease.
Обычный native EndTurn сохраняет доставку: отправитель сообщает EndTurnObserved
после успешной штатной Send, хост сообщает EndTurnApplied после штатного обработчика.
Сервер сопоставляет оба факта по epoch/lease в любом порядке; один факт недостаточен.

После пары свидетельств lease потребляется ровно один раз. Сервер глобально
сериализует engine-action транзакции, даже если оба игрока завершили ход одновременно:

1. ApplyTurnStart хосту для следующего дня нужного игрока; дождаться ActionResult.
2. ActivateTurn тому игроку с тем же actionId и новым lease; дождаться ActionResult.
3. Только после этого зафиксировать новый субъективный день и обрабатывать следующую заявку.

Нельзя заменять обычную доставку синхронным вызовом серверного метода, пропускать
EndTurnApplied, повторять Action после принятой записи или принимать duplicate ACK.
Успешная отправка в сокет не означает, что игра исполнила действие.

## Объединить ходы

| kind | Действие | Исполнитель |
| --- | --- | --- |
| 1 | ApplyTurnStart | host |
| 2 | ActivateTurn | Владелец нового хода |
| 3 | HoldInput | Пришедший к барьеру игрок |
| 4 | PrepareMerge | join, затем host |
| 5 | ExecuteMerge | host |
| 6 | ReleaseStock | join, затем host |

Если следующий день равен mergeDay, игрок удерживается в дне mergeDay−1 через
HoldInput с подтверждением. Когда удержаны оба, сервер отправляет PrepareMerge
join, затем host и ждёт оба результата. Затем ExecuteMerge хосту.
PrepareMerge, ExecuteMerge и ReleaseStock имеют один общий новый actionId,
playerHandle=hostHandle (включая отправку join), day=mergeDay, lease=0.
Успешный ActionResult и оба MergeApplied могут прийти в любом порядке; нужны все.
После этого ReleaseStock join, затем host (без ACK). При mergeDay=0 барьера нет.
Релиз обычных ходов — необратимый результат общего барьера, а не fallback при ошибке.

## Не обгонять игровые сообщения

Сетевой порядок нужен, но недостаточен: в MSS игровой пакет сначала попадает
в FIFO, затем в native receive, а часть команд — ещё и в стратегическую очередь.
Control не должен менять игровой день раньше применения предшествующего native
сообщения. Адаптер ведёт отдельные отметки обработки; снятие пакета из FIFO не ACK.
Deferred native receive сохраняет отметку до настоящей обработки. Предусмотренное
протоколом подавление stock-сообщения отличается от аварийного отказа обработки.
Native-пакеты после ожидающего control удерживаются до передачи этого control
в порт, но не до игрового ACK: последующий TurnInfo должен оставаться доступен
bootstrap. Так поздние команды не продлевают барьер более раннего control.

Сервер также сохраняет причинный порядок в fan-out: сначала результаты игрового
действия, затем соответствующий control. Нельзя рассчитывать на частоту кадров,
Sleep, задержку сети или отсутствие нагрузки. Подробности клиентского ожидания
находятся в `lobby_transport.cpp` и `netintercept.cpp`.

## Завершить или заменить карту

Любой отрицательный результат, нарушение протокола, disconnect или watchdog
завершает эпоху. Сервер очищает очередь действий, извещает доступных участников
Error/Abort, прекращает игровые мутации и завершает карту штатным terminal flow
лобби. UI должен показывать причину, а не выглядеть как бесконечно замороженный ход.

Референсные watchdog: 12 секунд на второй факт EndTurn после первого,
30 секунд на EngineAction, 15 секунд на CommitApplied/OperationalApplied после
соответствующего bootstrap fan-out. SessionActivated и BeginTurnApplied не
ограничиваются этим таймером ожидания человеческой готовности.
Проверять точные точки запуска/снятия таймеров по `coordinator.js`; не навешивать
один общий таймер на весь брифинг. Частично доставленный fan-out не атомарен:
откат уже применённых действий не заявляется.

Нет resend/retry/reset/reconnect внутри эпохи. Для новой карты (в том числе 111)
нужны штатное уничтожение старой карты и новая epoch. Клиент сначала закрывает
допуски и отменяет принадлежащую карте UI-работу, ждёт завершения native worker,
затем сбрасывает состояние и патчи. Хвосты старой epoch не применяются к новой.
Сервер не выдаёт следующий Arm до завершения teardown обеих сторон.

## Проверить серверную реализацию

`tools/simturns-relay/src/coordinator.js` и его тесты — исполняемый эталон автомата.
Он отделён от pipe/файлов; серверный адаптер должен сохранить порядок fan-out,
валидацию и terminal semantics. Это не готовая библиотека для C++ сервера.

Обязательные случаи: bootstrap обоих порядков свидетельств; одновременный EndTurn;
несколько независимых дней; merge с обоими порядками прибытия; старые/повторные
lease и actionId; неправильная сторона/epoch; каждый timeout; failure во время
fan-out; leave/disconnect; повторная карта с другой ролью; ОХ-клиент в обычной комнате;
клиент без capability в ОХ-комнате; malformed/truncated envelope и v8.

Отдельный следующий PR универсального харнеса должен прогнать одинаковые игровые
сценарии через локальный рилей и настоящий лобби-транспорт. Ни эта спецификация,
ни unit-тесты, ни исторические 18/18 не заменяют такой live-проверки.
