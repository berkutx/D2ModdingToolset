# Короткая игровая приёмка подготовленных матчей

**Это план, не отметка пройденного теста.** Два клиента из согласованной тестовой
установки, одинаковая новая DLL, `DisplayErrors=1` в `[Disciple]` действующего
`Disciple.ini`. Установку/резерв DLL согласует ответственный за выпуск. Не менять
пользовательские Lua/.dlg ради этого прогона. Использовать отдельную нерейтинговую
подготовку двух тестовых аккаунтов, не настоящий матч чемпионата.

Lua на сайте — пример, а не обязательная побайтовая версия хоста. Для новой
подготовки не требуется совпадение MD5 с примером и не сравнивается схема spins.
Клиент выбирает последнюю локальную версию по названию и основе имени файла,
сохраняя варианты вроде Duo/Trinity и авторские ответвления. Номер версии важнее
времени изменения файла. Для нераспознанной версии нужен точный basename.
После выбора проверяются согласованные значения по локальным диапазонам/шагам
и число игроков: ошибки не исправляются округлением или выбором старого Lua.

Начать с обычного двухместного шаблона и согласованных параметров; хосту задать
явную расу и тип лорда, отличающийся от его обычного выбора. Для каждого запуска
записать preparation/attempt IDs, локальные basename, display name и MD5 до старта
клиента. Эти MD5 нужны для фиксации фактически использованного файла, не для
сверки с примером сайта. Каталог неизменяем до перезапуска игры.

Строгие проверки FilesHash/TemplateHash при обычном входе и проверки продолжения
сохранённой игры не ослаблены. Рейтинговый допуск проверяется отдельно по
allowlist фактического Lua, а не по MD5 файла-примера. Основной прогон ниже —
нерейтинговый; не добавлять тестовые версии в рейтинговый allowlist ради приёмки.

| Шаг | Действие | Ожидаемый результат |
| --- | --- | --- |
| 1. Первый вход | Оба подтвердили условия на сайте; назначенный хост нажал запуск, затем вошёл в игровое лобби | Только у хоста штатное Yes/No с верными участниками, файлом-примером и условиями. Текст поясняет выбор локальной версии. До «Да» нет выбора/валидации локального шаблона, генерации и комнаты |
| 2. Отложить | Нажать «Нет», обновить страницу подготовки; повторить запуск новой попыткой | Первая попытка отложена, самоповторного окна нет. Новая попытка предлагает согласие один раз |
| 3. Занятое меню | Открыть на хосте справку/другое окно, затем запустить подготовку; закрыть окно | Предложение не перекрывает занятый UI, появляется после возврата в свободное лобби |
| 4. Preview | Согласиться, дождаться карты, нажать Retry, затем Cancel | Обычный preview, новая карта с теми же расами/spins. Cancel возвращает в лобби, комнаты нет; следующая попытка работоспособна |
| 5. Отмена сайта | Во время генерации либо готового preview изменить согласованные условия на сайте | После ACK старая карта не может создать комнату. Старый worker безопасно заканчивается, затем доступно новое предложение. Повторная отмена не оставляет генератор без рабочего возврата |
| 6. Принять и войти | Новая попытка → Accept; джойнер входит вручную | Одна связанная комната, хост имеет согласованные race/lord и корректный портрет. Джойнер выбирает свою расу/лорда сам по компактному системному сообщению. Поздняя отмена сайта не выкидывает из созданной комнаты |
| 7. Игра и возврат | Запустить карту, один `111` → Retry/Accept, завершить тестовую игру; предложить следующую подготовку | Оба загружают карту, `111` остаётся сегментом той же игры и использует принятый локальный recipe/filename. После штатного возврата хост снова получает предложение, не во время игрового перехода; каталог Lua не перечитывается |
| 8. Отсутствующий шаблон и текст | Отдельные подготовки: нет локального файла/семейства для предложения; длинные условия | Ошибка отсутствующего шаблона появляется только после «Да», комнаты нет: «не найден шаблон для матча, перезапустите клиент игры после добавления». Длинные условия доступны по страницам полностью |
| 9. Пересечение отмены | Accept и отмена сайта близко по времени; также отмена после появления комнаты | Если CreateRoom уже успешно завершён, комната остаётся, согласованный lord и портрет всё равно выставляются. Ранняя отмена по-прежнему блокирует создание |
| 10. Онлайн-хеш | Войти новой MSS без создания комнаты; проверить `GET /online`, выйти из игрового лобби, оставив веб-вкладку | `presence[].compatibility.filesHash` появляется после фонового расчёта, совпадает с обычным room FilesHash. После выхода — `game:false, compatibility:null` либо строки нет. Старый клиент остаётся работоспособным с `null` |
| 11. Другие байты локального Lua | Подготовить нерейтинговый матч с локальным Lua нужного имени/семейства, чей MD5 отличается от примера сайта; согласованные значения допустимы локально | После «Да» есть генерация/preview, после Accept — связанная комната. Нет ошибки `template-hash` и требования скачать точные байты примера. Отдельный рейтинговый допуск не наследуется от примера: используется allowlist фактического Lua |
| 12. Числовые версии и фактический filename | На хосте заранее подготовлены `Fight_1.9.lua` / `Fight-1.10.lua` с display names `Fight! 1.9` / `Fight! 1.10`; пример сайта — `Fight.lua`, `Fight! 1.4`. Условия подходят обоим; у 1.9 может быть более новое время файла | Выбрана 1.10. В preview/описании — локальная версия; после Accept room `TemplateName` и запись `Lobby create: template=...` указывают `Fight-1.10.lua`, а `TemplateHash` — MD5 его cached source, не примера. Retry и последующий `111` сохраняют выбранный filename/source |
| 13. Нестандартный суффикс | Пример имеет name `Outrunner 3.3K(2)` и filename `Outrunner_kotovasiya2.lua`; рядом установлен обычный Outrunner с большей числовой версией | Выбран только точный basename `Outrunner_kotovasiya2.lua`, без сверки MD5 с примером. Обычный Outrunner не подставляется. Без точного файла — ошибка после «Да», даже если рядом есть другие Outrunner |
| 14. Неоднозначная последняя версия | В отдельном наборе есть `Fight_1.10.lua` / `Fight-v1.10.0.lua`, оба `Fight!` соответствующей версии и с допустимыми параметрами | Явная ошибка нескольких локальных шаблонов одной версии после «Да»; нет генерации и комнаты. Не выбирается первый файл по алфавиту или времени; совпадение байтов тоже не разрешает неоднозначность |
| 15. Параметры новой версии недопустимы | Более старая версия принимает согласованные значения, последняя — нет. Отдельно проверить размер карты, диапазон/шаг spin, неизвестный индекс spin и число игроков | Ошибка параметров выбранной последней версии после «Да», комнаты нет. Значения не зажимаются в диапазон, не заменяются defaults, старая версия не выбирается автоматически. Изменение только имени/подписи spin не является отдельным schema-gate |
| 16. Разные варианты | Рядом стоят Duo/Trinity/Clover и авторский fork с большим номером; пример относится к одному варианту | Выбор остаётся в семье display name **и** основе filename. Другой вариант не подставляется даже при большем номере и одинаковом числе игроков |
| 17. Строгий вход и продолжение | Для комнаты шага 12 проверить обычный вход гостя с фактическим Lua хоста; отдельно — с иной версией Lua. Проверить штатное продолжение сохранённой игры с совместимым и заведомо несовместимым тестовым набором | Совместимый гость входит; другой локальный MD5 по-прежнему отклоняется обычной проверкой TemplateHash, FilesHash тоже сохраняется. Продолжение не получает обход своих прежних проверок совместимости. Послабление к примеру сайта действует только при выборе Lua для новой prepared-генерации |

Отдельная известная граница для воспроизведения: во время первоначального Setup
удерживать стороннюю модалку дольше 15 секунд, затем проверить lord/портрет.
Общий deadline сейчас включает это ожидание, поэтому применение лорда не
гарантируется. Не записывать этот случай как пройденный на основании Cancel-fix.
На медленном диске отдельно проверить первый login и выход во время хеширования:
worker не обращается к UI, но уничтожение сервиса ждёт его завершения.

Для шагов 11–16 заранее согласовать отдельные тестовые Lua в тестовой установке;
не переписывать пользовательские шаблоны и не подменять файлы запущенной игры.
Примеры сайта менять только через штатную админку, используя отдельные тестовые
записи и не публикуя их для рейтинга. После изменения набора локальных файлов
перезапустить клиент: простого возврата в главное меню недостаточно. Для
положительного входа у гостя должен быть именно выбранный локальный Lua хоста,
а не обязательно файл-пример с сайта. Если оба клиента используют одну папку,
отрицательные проверки с разными файлами требуют заранее согласованных раздельных
тестовых наборов; не имитировать их подменой Lua у работающего хоста.

На первом `Missing control`, неверной расе/портрете, зависшем возврате или второй
комнате остановить прогон: сохранить текст окна/скриншот, UTC-время, attempt ID и
соответствующий участок `mssProxyError.log`/`mssProxy.log`, если эти журналы включены.
Не скрывать ошибку настройкой `DisplayErrors=0` и не повторять запуск вслепую.
Редкий отказ native createServer после серверного CreateRoom не провоцировать
порчей игровых файлов: исправление проверено по существующему normal-flow cleanup,
реальное воспроизведение отмечается отдельно, если встретилось.

Автоматические тесты wire/settings/lifecycle и статическое native-доказательство
описаны в [контракте клиента](PREPARED_MATCHES.md) и
[RE-отчёте](2026-09-20_reverse-prepared-native-report.md). Они не заменяют эти шаги.
